## Confirmed (adversarially verified)

### [CRITICAL] Initial sync deadlocks: restore branch is unreachable and push collides with server unique constraints under divergent UUIDs

**Where:** `App/Sources/Supabase/SyncModel.swift:68`

initialSync() (SyncModel.swift:62-77) only restores when `localWorkouts == 0 && serverWorkouts > 0`, otherwise it pushes. But AppModel.openAndSeed() (App/Sources/AppModel.swift:128-133) auto-imports the bundled strong_workouts.csv on ANY install where workoutCount == 0, and StrongImporter mints fresh random UUIDs per install (Records.swift:10-70 `UUID().uuidString` defaults). So on a fresh install + sign-in to an existing account, localWorkouts > 0, the push branch runs, and every imported row is upserted under NEW ids while the server already holds the same rows under the OLD device's ids. The server then rejects them via `unique("userId", name)` on exercise (0001_init.sql:11) and `unique("userId", "startedAt", name)` on workout (0001_init.sql:41) with 23505. push() catches, sets status = .error, and the outbox is never cleared (SyncModel.swift:129 runs only after full success), so every subsequent push replays the same conflicting upserts: sync is permanently wedged. The same happens if a user imports their Strong CSV on a second device before signing in, and (for exercises) whenever two signed-in devices independently create an exercise with the same name. The restore path effectively never runs whenever the bundle CSV ships.

**Suggested fix:** During initial sync, reconcile by natural key instead of blind push: fetch server exercises/workouts, map local rows whose (name) / (startedAt, name) match server rows onto the server ids (rewriting child FKs), then push only genuinely new rows. Alternatively make the exercise upsert use onConflict: "userId,name" (and workout onConflict: "userId,startedAt,name") so pushes merge instead of violating, and stop gating restore on workout count alone.

### [CRITICAL] Sign-out/sign-in as a different user leaks first user's data into second user's cloud account

**Where:** `App/Sources/Supabase/SyncModel.swift:54`

signOut() (lines 54-58) only clears the Supabase auth session; the local SQLite store, sync outbox, and lastSyncedAt survive. When a DIFFERENT user then signs in, initialSync (lines 62-77) sees localWorkouts > 0 and calls push(), draining the outbox into the new user's account. If the first user never signed in, the v2-outbox migration (FitnessKit/Sources/FitnessKit/Database/AppDatabase.swift:105-108) seeded the outbox with every existing row, so the ENTIRE first user's history uploads into the second user's account. Even with an empty outbox: the second user sees the first user's local history in-app, their own cloud data is never restored (restore only runs when localWorkouts == 0), and if the first user had synced, any later edit to one of their rows pushes an upsert whose id exists on the server under the first user's userId — RLS (supabase/migrations/0001_init.sql:87-97) rejects it and sync wedges permanently in .error with the outbox never draining.

**Suggested fix:** Record the authenticated user id locally (e.g. UserDefaults) on sign-in. On sign-in with a different user id than the one the local DB was last synced under, either wipe the local DB + outbox and restore from the server, or prompt the user to choose. Never blind-push an outbox produced under a different (or no) account; consider clearing local data on signOut as well.

### [HIGH] Decimal weights cannot be typed: weight binding re-formats on every keystroke and drops the decimal separator

**Where:** `App/Sources/Views/ActiveWorkoutView.swift:363`

SetRow's weightBinding getter derives the text from model state (`set.weight.map { Format.weight($0) } ?? ""`) and the setter immediately writes through `session.updateSet(...)`. `updateSet` (WorkoutSessionModel.swift:188-194) mutates the `exercises` array of an @Observable class, which fires an observation even when the numeric value is unchanged, so the TextField's text is reset from the getter after every keystroke. Typing "187" then "." parses as Double("187.") = 187.0, the getter re-renders "187", and the decimal point vanishes — sequentially typing "187.5" yields "1875". Fractional weights (187.5, 22.5, plate math staples) are effectively impossible to enter. Additionally `Double(text)` only accepts "." as the decimal separator: on comma-decimal locales the `.decimalPad` keyboard offers ",", and typing it makes `Double("82,5")` return nil, which clears the stored weight and blanks the field.

**Suggested fix:** Hold the field text in local @State (seeded from the set) and commit to `session.updateSet` on focus loss / submit, or only push the parse back to the model when `Double(text)` differs from the current value and keep the in-progress string authoritative while the field is focused. Parse with a locale-aware formatter (e.g. `Decimal(string:locale:)` or `Double(text.replacingOccurrences(of: ",", with: "."))`).

### [HIGH] Strong import idempotency breaks when device timezone changes, duplicating every workout

**Where:** `FitnessKit/Sources/FitnessKit/Import/StrongImport.swift:30`

StrongImport.parse sets `dateFormatter.timeZone = .current` (StrongImport.swift:30), so a CSV timestamp like "2025-01-05 10:00:00" parses to a different absolute Date depending on the device's timezone at import time (verified: America/Los_Angeles vs Europe/London differ by 28800s for the same string). StrongImporter's idempotency check (StrongImporter.swift:26-28) and the unique index on workout(startedAt, name) (AppDatabase.swift:42) both key on the parsed Date. If a user imports, then travels or moves timezone, and re-imports the same export (the documented-safe operation per the comment at StrongImporter.swift:11-12), every workout re-parses to a shifted startedAt, the exists-check misses, and the entire history is inserted a second time — duplicated PRs, doubled volume, and inflated weekly streak counts, all synced to Supabase.

**Suggested fix:** Make parsing deterministic: pin the formatter to a fixed timezone (e.g. UTC), or dedupe on the raw CSV wall-time string instead of the parsed Date (e.g. compare against startedAt re-formatted with the same formatter, or store an import key of (dateString, name)).

### [HIGH] restore() silently truncates data at PostgREST's 1000-row cap (no pagination)

**Where:** `App/Sources/Supabase/SyncModel.swift:224`

fetchAll() (SyncModel.swift:224-226) does `client.from(table).select().execute().value` with no `.range()`/pagination. Supabase's hosted PostgREST caps responses at max_rows = 1000 by default, and returns the first 1000 rows without error. Any real account exceeds 1000 workoutSet rows after a single Strong import (each workout contributes many sets), so a fresh-install restore silently rebuilds only part of the user's history — sets, items, or workouts past row 1000 are dropped. Worse, if a parent workout lands past the cap while its workoutItems are within it (row order is unspecified without .order()), the local FK insert in the restore transaction (SyncModel.swift:206-220) throws and the entire restore fails. Nothing ever re-fetches the missing rows: subsequent syncs are push-only.

**Suggested fix:** Page through each table with `.order("id").range(from:to:)` in a loop until a short page is returned (or use explicit `.limit()` with keyset pagination), and add a deterministic order so parent/child fetches are consistent.

### [HIGH] restore() deletes pre-existing outbox rows, permanently orphaning local-only data

**Where:** `App/Sources/Supabase/SyncModel.swift:219`

restore() ends with `DELETE FROM outbox` (SyncModel.swift:219), justified by the comment that the restore's own trigger-generated rows are already on the server. But the DELETE is unconditional: it also wipes outbox entries that existed BEFORE restore ran. Concrete scenario: fresh install (assume no bundled CSV), user logs body-weight entries or creates a template/exercises (zero workouts), then signs into an existing account with server workouts — initialSync takes the restore branch (localWorkouts == 0 && serverWorkouts > 0, line 68). The user's local bodyWeight/template rows survive in SQLite, but their queued upserts are deleted from the outbox and, since nothing ever updates those rows again, they are never backed up. The loss is silent — status goes .idle and lastSyncedAt is stamped (line 221).

**Suggested fix:** Before the write transaction, read `MAX(seq)` from the outbox; inside the transaction delete only `WHERE seq > preRestoreMaxSeq` (the rows generated by the restore's own saves), leaving pre-existing entries to be pushed normally afterward — then call push().

### [HIGH] ExerciseChartCard evaluates yDomain per point inside the mark ForEach — O(n^2) recompute of chartPoints on every render, up to 120x/sec while scrubbing

**Where:** `App/Sources/Views/ExerciseChartCard.swift:130`

All chart data is derived in computed properties that recompute from scratch on every body evaluation: chartPoints (line 52, O(n) compactMap over all sessions with a new array allocation), segments (line 65, calls chartPoints), xDomain (line 88, calls chartPoints), visiblePoints (line 100, calls chartPoints + O(n) filter), yDomain (line 105, calls visiblePoints). The killer is line 130: `yStart: .value("Base", yDomain.lowerBound)` sits inside `ForEach(segment.points) { point in ... }`, so yDomain — which itself walks chartPoints twice (compactMap + filter + min/max) — is evaluated once per data point. For an exercise trained weekly for 8 years (~300 sessions out of the 736 workouts), one chart build costs ~300 x ~900 = ~270k date/compare operations plus ~300 fresh [ChartPoint] array allocations, on top of rebuilding ~600 AreaMark/LineMark entities. Because scrubbed and crosshair are @State on this same view (lines 20-21), every DragGesture.onChanged event (60-120 Hz on ProMotion) invalidates body and repeats the whole thing — millions of ops per second during a scrub, which is exactly the interaction that must stay at frame rate. The drag handler additionally recomputes visiblePoints (O(n)) per touch event at line 179. The same body invalidation also re-runs segments/xDomain/visibleXDomain/count checks, so chartPoints alone is rebuilt 5+ times per frame even before the per-point yDomain cost.

**Suggested fix:** Hoist the derived data out of the per-render path: compute chartPoints/segments/xDomain/yDomain once into @State (or plain lets at the top of body) and refresh them only in onChange(of: metric) / onChange(of: zoom.domain) — the underlying sessions are immutable for the life of the view. At minimum, bind `let yLower = yDomain.lowerBound` before the Chart and use it in the AreaMark so yDomain is evaluated once per render instead of once per point, and capture `let points = chartPoints` / `let segs = segments` / `let visible = visiblePoints` as locals so each is computed exactly once per body evaluation.

### [HIGH] Finishing a workout with zero completed sets creates a permanent empty history entry

**Where:** `App/Sources/Views/ActiveWorkoutView.swift:522`

The FinishSheet's 'Finish Workout' button (ActiveWorkoutView.swift:522-527) calls session.finish() with no guard on completedSets. SessionStore.finish (FitnessKit/Sources/FitnessKit/Database/SessionStore.swift:129-145) deletes all sets with completedAt IS NULL, then all items left with no sets, then stamps finishedAt — producing a finished workout row with zero exercises. It appears in HistoryView and month workout/duration totals (AppModel.loadEverything), syncs to Supabase, and since no view offers workout deletion (HistoryView/WorkoutDetailView have none), the empty entry is permanent. This matches the empty-history-entry bug seen in practice.

**Suggested fix:** In finish flow, when session.completedSets == 0, treat Finish as discard: call SessionStore.discard instead of finish (optionally with a confirmation alert like 'No sets completed — discard this workout?'). Alternatively have SessionStore.finish delete the workout row when no items remain after pruning.

### [HIGH] Finishing a stale (6h+) workout stamps finishedAt = now, recording massively inflated durations

**Where:** `FitnessKit/Sources/FitnessKit/Database/SessionStore.swift:129`

The stale prompt's 'Finish it' (ActiveWorkoutView.swift:80) runs the normal finish path: SessionStore.finish defaults finishedAt to Date(), and WorkoutSessionModel.finishSummary (WorkoutSessionModel.swift:153) computes duration as Date().timeIntervalSince(startedAt). A workout started yesterday and finished from the stale prompt is recorded with a 20+ hour duration, inflating LoadedWorkout.durationSeconds, the History month totalSeconds (App/Sources/AppModel.swift:204), and the finish-sheet stats. The whole point of the stale prompt is recovering an abandoned session, so this path is expected, not exceptional.

**Suggested fix:** When finishing, cap finishedAt at the last completed set's completedAt (falling back to startedAt + a small floor) whenever now - lastActivity exceeds a threshold; pass that timestamp to SessionStore.finish(at:) and use it in finishSummary's duration.
